## 1. ภาพรวมผลิตภัณฑ์และขอบเขตการส่งมอบ (Product Overview & Deliverable Scope)
- **แอปส่งมอบหลัก (Deliverable Application):** TukDaeng Back Office — responsive web application สำหรับทีมภายใน ใช้ดูแลและปฏิบัติการระบบ TukDaeng หลังผู้ใช้ FO (Front Office mobile app) สร้างข้อมูลหรือกิจกรรม เช่น marketplace, social, support, content และ notification. BO แยกจาก FO mobile app ชัดเจน — Admin ไม่ใช่ admin access ใน FO
- **กลุ่มผู้ใช้งานเป้าหมาย (Target Personas):** ทีมภายในของ TukDaeng ที่ใช้ BO ผ่านบัญชี `Admin` (ชนิดบัญชี admin เพียงแบบเดียว) โดยหน้าที่งานแยกตาม Roles & Permissions ไม่ใช่ประเภทบัญชี — ครอบคลุม persona ด้าน operation ทั้งหมด: ผู้ดูแลระบบ (Super Admin / Admin Manager), ทีมปฏิบัติการ (Operations Manager), ฝ่ายช่วยเหลือผู้ใช้ (Support Agent), ทีม moderation (Trust & Safety Moderator, Asset Operations), ทีม content (Content Editor / Content Publisher) และทีม market master data — ทำงานบน desktop/tablet เป็นหลัก โดย mobile-width browser ต้องใช้ค้นหา ดู detail review approve/resolve และ emergency moderation ได้
- **เป้าหมายทางธุรกิจและขอบเขตระบบ:** โจทย์หลักคือ operational control + trust & safety + auditability — Admin ต้องจัดการ users, assets, content, market data, support และ notifications ได้ พร้อม review report/moderation, suspend/ban users และ trace ทุก sensitive action ด้วย audit trail (before/after, actor, timestamp, reason) และทุก BO action ที่กระทบ public surface ต้อง sync ผลกลับ FO (Feed, Asset Detail, Board, Search, Profile, Watch Alert, Notification) — ขอบเขตตรวจรับงานแยกเป็น phase: **Phase 1** (ล็อกใน prototype แล้ว) = Global Rules, Auth/Admin Accounts, Admin Permission, Dashboard, User Management, Asset Management (รวม Reported Assets/Comments), Content Management, Market Data, Option Master (รวม Suggestion Queue), Market Demand (Demand Overview, Search Insights, Watch Alert List/Detail — read-only), Help & Support (Policy & Versioning + Support Center), Account Deletion, Audit Log และ Admin Settings (Admin Accounts, Roles & Permissions, Delivery Logs); **Phase 2** = Directory, Reports & Analytics, Notifications (Broadcast & System Templates), Chat moderation; **Phase 3** = advanced moderation workflow และ external integrations — Directory ถูกเลื่อนจาก Phase 1 จนกว่า FO directory detail routes จะเปิด ห้าม expose menu/route ใน Phase 1

## 2. [มิติที่ 2] กฎทางธุรกิจที่ซับซ้อนและสูตรคำนวณ (Business Logic, Rules & Financial Formulas)
> ระบุกฎทางธุรกิจ เงื่อนไขซ้อนทับ สูตรคำนวณการเงิน/คะแนน หรือนโยบายที่ไม่ใช่แค่หน้าจอ CRUD ทั่วไป
- **สูตรคำนวณหลัก / เงื่อนไขการคิดเงินหรือคะแนน:**
  - **Price Index FX Conversion (Market Data):** Provider price จาก The Watch API ที่เป็น USD ต้องเก็บ `source_currency`, `source_price`, `converted_price_thb`, `fx_rate`, `fx_rate_date`, `provider_updated_at`, `synced_at` ครบทุก field — ราคาที่แสดงใน BO/FO เป็น THB เสมอ (BO timezone `Asia/Bangkok`, currency THB เป็น global rule); FO ห้ามเรียก provider โดยตรง อ่านจาก TukDaeng internal API/cache เท่านั้น และ price index เป็น valuation source priority แรกของ FO Portfolio เมื่อข้อมูลเพียงพอ — asset ที่เป็น `Permanently Hidden` หรือ `ลบโดยเจ้าของ` ต้องไม่ถูกนับใน portfolio value / asset value summary
  - **Report escalation threshold (Asset):** นับ unique reporter ต่อ report case — 1 unique reporter = สร้างเคส `Pending` (asset แสดงตาม status เดิม); 3 unique reporters = ยกระดับเป็น review priority; 5 unique reporters = ระบบซ่อนชั่วคราวอัตโนมัติ (`Auto Hidden`) แต่เฉพาะ asset ที่ยังเป็น `Sale` หรือ `Show` — ถ้าเป็น `Hide`/`Sold` อยู่แล้วไม่ซ่อน เก็บเคสไว้ให้ Admin ปิด ทุกขั้นมี audit
  - **Report priority score (User):** คะแนนความสำคัญคำนวณจาก unique reporter — 1–2 reporters = Low (ปกติ), 3–4 = Medium (กลาง) เพื่อเร่ง review, 5+ หรือ evidence รุนแรง = High (สูง) ใช้เป็นเงื่อนไขประกอบการ suspend ระหว่างตรวจสอบ — priority ไม่เปลี่ยนสถานะบัญชีอัตโนมัติ
  - **Watch Alert match evaluation:** Match เฉพาะ asset status `Sale` ที่ผ่าน moderation/visibility rule และไม่รวม asset ของ blocked user/คู่ที่ block กัน — option-based criteria (condition, delivery, case material, movement, dial color, strap/bracelet) match ด้วย relation id เท่านั้น ส่วน free-text spec (`ระบุเอง`) match ได้แค่ผ่าน keyword criteria บน snapshot text จนกว่า BO curate แล้ว backfill relation id — notification dedup ด้วย (`alert_id`, `asset_id`) ห้าม notify asset เดิมซ้ำใน alert เดียวกัน
- **กฎการตรวจสอบเงื่อนไขและข้อยกเว้น (Edge Cases & Cutoff Rules):**
  - **Asset status lifecycle (owner-controlled × moderation overlay):** Status ของ owner (`Sale`/`Show`/`Hide`/`Sold`) แยกจาก moderation overlay (`Admin Hidden`/`Auto Hidden`/`Permanently Hidden` + retention state `ลบโดยเจ้าของ`) — Admin ห้ามเปลี่ยน owner-controlled status โดยตรง ใช้ได้แค่ moderation action: ซ่อนชั่วคราวทำได้เฉพาะ `Sale`/`Show` (คง status เดิม), ยกเลิกซ่อนชั่วคราวทำได้เฉพาะ `Admin Hidden`/`Auto Hidden`, ซ่อนถาวรทำได้กับ `Sale`/`Show` และ asset ที่ซ่อนชั่วคราวอยู่ (owner เห็น read-only, แก้ไข/republish/ลบเองไม่ได้), ห้ามเปลี่ยนสถานะรายการหลัง `Permanently Hidden` — ถ้า owner เปลี่ยนเป็น `Hide`/`Sold` ก่อน Admin action ระบบต้องห้ามซ่อนชั่วคราวและแสดง current status ล่าสุด
  - **Report/moderation workflow (post-close locking):** Report status `Pending` → `Closed` เป็นทิศเดียว — `Closed` เป็น final state ไม่มี reopen action; asset ที่ถูกซ่อนชั่วคราวต้อง restore หรือซ่อนถาวรก่อนจึงปิดรายงานได้; post-only feed post (kind `post`, ref `POST-`) เข้า BO เฉพาะผ่าน Reported Assets / Reported Comments queue เท่านั้น ไม่มี list แยก — comment moderation มี lifecycle แยก `Visible`/`Hidden`/`Removed`/`User Deleted` พร้อม action Hide (ไม่ปิดเคส) / Restore (ปิดเคสอัตโนมัติ) / Remove (ปิดเคสอัตโนมัติ, restore ไม่ได้) / Close no violation (ไม่เปลี่ยน comment, ไม่ส่งอีเมล) — action อื่นทุกตัวต้องส่งอีเมลแจ้ง author ผ่าน registered email นับ reporter แบบ unique (report ซ้ำจาก user เดิมไม่เพิ่ม count)
  - **User account lifecycle:** `Pending Verification` / `Active` / `Suspended` / `Banned` / `Deletion Requested` / `Deleted` — Suspend ใช้กับ Active/Pending Verification, Ban ใช้กับ Active/Suspended, Unsuspend/Unban กลับ Active; `Suspended`/`Banned` ต้อง revoke/block session และ login ไม่ได้; report user ไม่เปลี่ยนสถานะอัตโนมัติ รอ Admin action; `Guest` ไม่ใช่ user status และ `Deleted` เป็น read-only historical state ไม่มี action ลบโดยตรงใน User List
  - **Account deletion lifecycle (30-day grace period):** FO confirm Delete → ระบบทำ atomically: ระงับบัญชี (`Deactivated`) + revoke session + ซ่อน public profile/assets ทันที + ปิด report ที่เปิดอยู่อัตโนมัติ + สร้าง request เข้าคิว `รอดำเนินการ` — ช่วง grace period 30 วัน: user sign-in ด้วยบัญชีเดิม = cancel deletion + restore ทันที (login-to-restore) หรือ Admin กด `คืนบัญชี`/`ปฏิเสธคืนบัญชี` (ปฏิเสธ = block self-restore แต่ไม่เริ่มนับใหม่) — ครบ 30 วัน system job ลบบัญชีอัตโนมัติ (เก็บถาวร + ลบตัวตนในขั้นเดียว สถานะ `ลบตัวตนแล้ว`/`Anonymized` คืนไม่ได้) — lifecycle email 5 จุด: ยืนยันลบบัญชี / เตือนใกล้ครบ grace (ล่วงหน้า 7 และ 3 วัน) / คืนบัญชีแล้ว / ปฏิเสธคืนบัญชี / ลบตัวตนแล้ว (ต้องส่งก่อน anonymize) — หลังลบตัวตน สมัครใหม่ด้วยอีเมลเดิมได้เป็นบัญชีใหม่ ไม่เชื่อมประวัติเดิม
  - **Policy version state machine:** `Draft` → `Published` → `Archived` — มี `Published` ได้ 1 เวอร์ชัน และ `Draft` ได้ไม่เกิน 1 เวอร์ชันต่อ policy type (Phase 1 = Terms of Use + Privacy Policy เท่านั้น, fixed list); Publish Draft = เวอร์ชันใหม่ Published + เวอร์ชันเดิม Archived อัตโนมัติ + trigger FO re-consent sheet ทุก session; Restore Archived = สร้าง Draft ใหม่ (ไม่เปลี่ยนต้นทาง ต้อง Publish ใหม่); เนื้อหา TH/EN บังคับครบทั้ง 2 ภาษาก่อน Publish, change summary required
  - **Article lifecycle + scheduling:** `Draft`/`Scheduled`/`Published`/`Archived` — เลือก `Scheduled` ต้องกรอก publish date+time และห้ามย้อนหลัง (timezone `Asia/Bangkok`); Published ว่างเวลา = set เป็นเวลาปัจจุบัน; Cancel schedule กลับ `Draft`; Archive นำออกจาก FO Board/Search/Category (direct link แสดง unavailable); Restore กลับ `Published`; edit บทความ Published/Archived ต้องคง lifecycle status เดิม — FO Board Main เลือกบทความอัตโนมัติจาก `status=Published` + `category.status=Active` เท่านั้น
  - **Option Master + suggestion curation:** 4 กลุ่มรองรับ `ระบุเอง` (`case_material`, `movement`, `dial_color`, `strap_bracelet_type`) — free-text ถูก normalize (trim/collapse/lowercase) แล้วเช็คซ้ำ option label + `spec_option_aliases` ใน group; match = auto-link relation id ทันที, ไม่ match = save ด้วย relation `null` + snapshot text แล้ว upsert `spec_option_suggestions` (unique ด้วย `(group_id, normalized_text)`, `usage_count` +1 แทน row ซ้ำ) — curation queue มี 3 action: Promote (สร้าง option จริง + backfill relation id ให้ asset เดิม), Map alias (ผูกเป็น alias ของ option เดิม + backfill + auto-link ครั้งถัดไป), Ignore (ปิดโดยไม่สร้าง option — ไม่ใช่ block ถาวร ยังนับ usage ต่อและเปิด resolve ใหม่ได้) — **ห้าม auto-promote** ไม่ว่า usage_count สูงแค่ไหน; suggestion ที่ยังไม่ promote ต้องไม่แสดงใน FO dropdown/filter/criteria; resolved (`promoted`/`mapped`) ห้ามกลับเป็น `pending`
  - **Market data dependency (no current listing vs inactive):** entity/option `is_active=true` แต่ไม่มี Asset Sale = "no current listing" (unmet demand ปกติ ไม่ flag) แยกจาก `is_active=false` = "inactive market data" (หยุด trigger ใหม่ แต่เก็บ alert/history + แสดง dependency warning ใน Watch Alert List/Detail) — owner save แล้ว provider sync ห้าม overwrite ค่าที่ Owner กรอกเอง
  - **Admin identity lifecycle quotas/cutoffs:** Invitation token one-time อายุ 72 ชั่วโมง, Resend cooldown 60 วินาที + quota 5 successful issuances/rolling 24h ต่อ target (นับเฉพาะ commit สำเร็จ; hidden IP/device controls ห้ามเปิดเผย quota), `Pending` invitation มีได้เพียง 1 record ต่อ account (enforce ด้วย unique partial constraint ไม่ใช่ application check), token CSPRNG ≥256 bits เก็บเฉพาะ keyed hash/MAC — Reset token อายุ 30 นาที one-time ใช้แล้ว supersede, eligible เฉพาะ `Active` + `Locked`-from-failed-login — Failed login 5 ครั้ง → lock 15 นาที; Change Password wrong-current 5 ครั้งติด → block 15 นาที (prototype simulation 60 วินาที) — session idle 8 ชั่วโมง / max 24 ชั่วโมง
  - **Dedup prevention / ป้องกันข้อมูลซ้ำซ้อน:** unique reporter count ต่อ report case; Watch Alert notification dedup (`alert_id`, `asset_id`); suggestion dedup `(group_id, normalized_text)` + alias dedup; admin email unique; invitation `Pending` 1 record ต่อ account; ทุก mutation มี `idempotency_key` (key เดิมคืนผลเดิม, key เดิม payload ต่าง reject) + `expected_*_revision` optimistic concurrency — stale/no-op/race request ต้องไม่เกิด partial mutation และไม่สร้าง audit เมื่อ reject ที่ boundary; legacy audit alias (`ADMIN_ACCOUNT_INVITE`) ห้ามเขียนซ้ำกับ canonical event (`ADMIN_INVITATION_CREATE`) ใน mutation เดียว

## 3. [มิติที่ 6] ความปลอดภัย สิทธิ์การใช้งานหลายระดับ และธรรมาภิบาลข้อมูล (Security, RBAC & Compliance)
- **การยืนยันตัวตน (Authentication & SSO):** BO authentication แยกจาก FO โดยสมบูรณ์ — FO user login เข้า BO ไม่ได้ และ BO ไม่ใช้ Apple/Google SSO หรือ external IdP ใน V1; login baseline คือ `Email + Password → BO` เท่านั้น (ไม่มี Login OTP/MFA/2FA ใน current phase); session รองรับ JWT + refresh token หรือ secure session model ที่เทียบเท่า — idle timeout 8 ชั่วโมง, max session 24 ชั่วโมง; failed login 5 ครั้ง → lock 15 นาที; Forgot Password ตอบ generic response เสมอ (ไม่เปิดเผย account existence/eligibility) + reset token อายุ 30 นาทีแบบ one-time; admin activation ผ่าน one-time invitation link อายุ 72 ชั่วโมง (possession verification ไม่ใช่ login challenge); password policy ≥12 ตัวอักษรครบ uppercase/lowercase/number/special; session ถูก revoke/block เมื่อ account เปลี่ยนเป็น Locked/Suspended/Archived — My Account self-service (self-only enforced ที่ route/API/service): Change Password (สำเร็จ revoke session อื่นทั้งหมดคง current ไว้), Active Sessions (masked session ID/IP, individual revoke เฉพาะ session อื่น), Logout All Devices (all-or-nothing revoke รวม current)
- **การแบ่งระดับสิทธิ์และขอบเขตข้อมูล (RBAC / Multi-Tenant Isolation):**
  - โมเดลสิทธิ์: BO มีชนิดบัญชี admin เพียงแบบเดียวคือ `Admin` (ไม่มี sub-type) — ความแตกต่างของสิทธิ์กำหนดผ่าน **Roles & Permissions**: 8 System Role templates (ห้ามลบ/เปลี่ยนชื่อ/เปลี่ยน baseline จาก UI) + Custom Role ที่สร้างแบบ `from_scratch` เท่านั้น (ไม่มี copy/clone/duplicate flow); account ผูก `role_id` ไม่ผูกสิทธิ์เฉพาะบุคคล; permission enforcement ใช้ explicit permission keys (เช่น `<module>.view`, `<module>.manage`, `<module>.publish`, `<module>.sensitive.reveal`, `settings.admin_accounts.manage`, `audit.export`) ตรวจที่ navigation, route, UI action, API, service, export, sensitive-field และ audit layer — การซ่อนปุ่มใน UI อย่างเดียวไม่เพียงพอ ทุก mutation ต้องตรวจสิทธิ์ server-side ก่อนเขียน; permission result 5 ระดับ: `none` (ซ่อนเมนู + reject direct URL/API) / `view` / `manage` / `approve` (high-risk: confirmation + reason + before/after diff + audit) / `admin` (settings/role/policy + safeguard เพิ่ม)
  - Baseline permission matrix ของ 8 System Roles (สรุปจาก `16_ADMIN_SETTINGS_MODULE.md` §9.3 — level: admin/approve/manage/view/none):

  - Safeguard กันระบบล่มจากสิทธิ์: **master admin หลัก** (ADM-010) ห้าม suspend/archive/change role; **self protection** ห้าม action กับตัวเอง; **last active admin protection** ห้าม suspend admin คนสุดท้ายที่ยัง Active (ป้องกัน BO ไม่มีผู้ดูแล); Change Role ต้องผ่าน safeguard validation ทุกครั้ง (self-change, master, last admin-capable, downgrade จาก role ที่จัดการ role ได้, account status ไม่อนุญาต) — ล้มเหลวต้องไม่บันทึก mutation แสดง policy-blocked state
  - ไม่มี multi-tenant isolation — BO เป็น single internal workspace ของทีม TukDaeng; data scoping ทำด้วย permission level + sensitive-data policy แทน tenant boundary
- **การบันทึกประวัติตรวจสอบ (Audit Trail & Data Protection):**
  - Audit log required สำหรับ create, update, delete, publish, archive, suspend, ban, flag, remove, export, template update, permission update และ login/security events — schema บังคับ: Audit ID (immutable), timestamp (store UTC / display `Asia/Bangkok`), Actor Type (Admin/System/ProviderJob) + Actor ID + actor access context, Action Type, Target Entity Type/ID, Before/After value, Reason (บังคับเมื่อ destructive/public-impact), IP/Session/User Agent, Result (Success/Failed/Partial/Skipped), Error Code, FO Impact, Correlation ID — record เป็น immutable แก้ไข/hard delete จาก UI ปกติไม่ได้ (redact ตาม legal = สร้าง redaction event แยก), audit write ต้องสำเร็จก่อนหรือพร้อมกับ mutation สำคัญ (write fail = block high-risk action; low-risk เข้าคิว reliable retry)
  - ห้ามเก็บ secret ใน audit/delivery payload: plaintext password, password hash, OTP, raw/hashed invitation-reset token, raw session token, provider credential, idempotency secret — ห้ามทั้งใน UI, DOM, log, analytics และ test artifact
  - Sensitive data mask เป็น default (email, phone, LINE, purchase price/date/from, proof of payment, sold history, session metadata) — reveal ได้เฉพาะเมื่อมี business reason + policy permission + audit ทุกครั้ง; export ต้อง audit ตัวเอง + scope control + background job สำหรับขนาดใหญ่ + file expiry/controlled access
  - PDPA/compliance baseline: retention schedule ตัดสินแล้ว (DEC-53, `docs/pdpa-data-processing-register.md` §3) — consent record เก็บอายุบัญชี + 2 ปีหลังลบ, chat mask ตัวตน + purge เนื้อความ 1 ปี, report/moderation 2 ปีหลังปิดเคส, session/login metadata 90 วัน, deletion archive 5 ปี, audit log ≥1 ปี (security/sensitive 2 ปี), delivery/notification logs 1 ปี, export files ลบภายใน 7 วัน — DSR เป็น manual SOP (ไม่ build feature ใน V1) ตอบภายใน 30 วันตาม PDPA §31 (`docs/pdpa-dsr-sop.md`); breach response adopt `docs/pdpa-breach-runbook.md` (แจ้ง PDPC ≤72 ชม. ตาม PDPA §37(4)); publish policy ใหม่ trigger re-consent อัตโนมัติทุก FO session — security baseline: HTTPS, IP whitelist option สำหรับ production, provider API token เก็บใน backend secret เท่านั้น, FO ห้ามเรียก The Watch API โดยตรง

## 4. [มิติที่ 7] ความเสถียร การรองรับโหลด และเป้าหมายระดับบริการ (Reliability & SLA Targets)
- **ปริมาณการใช้งานและโหลดพร้อมกัน (Target Concurrency & Volume):** ยังไม่มีตัวเลข concurrent user/data volume target ที่ตัดสิน — สเปกกำหนด performance baseline เท่านี้: Dashboard ต้อง load ภายใน 3 วินาทีหลัง auth; table ขนาดใหญ่ต้องใช้ server-side pagination/filter/sort (prototype เป็น client-side mock เท่านั้น); page size มาตรฐาน 10 รายการ/หน้า; export ขนาดใหญ่ต้องรันเป็น background job; `listing_count` บน FO autocomplete เปลี่ยนบ่อย ต้อง cache แยกจาก market data catalog หรือดึง on-demand; BO ต้องใช้งานได้ครบบน mobile-width/tablet/desktop (งาน bulk ที่ซับซ้อน optimize สำหรับ desktop/tablet)
- **ความถูกต้องของธุรกรรม (Transaction & Consistency Guarantees):** core mutation + audit + transactional outbox ต้อง commit/rollback พร้อมกัน (atomic) — ไม่มี partial mutation; ทุก mutation รับ `expected_*_revision` + `idempotency_key` + `correlation_id` — stale/no-op/race/duplicate request ต้องถูก reject โดยไม่ mutate และไม่สร้าง audit; exact retry ด้วย idempotency key เดิมคืนผลเดิม (key เดิม + payload ต่างต้อง reject); concurrent submit มีผู้ชนะ 1 คำขอ (เช่น invitation activation คนอื่นได้ safe `used/stale` result); invariant ที่ enforce ด้วย DB constraint ไม่ใช่ application check เท่านั้น: invitation `Pending` ≤1 record/account (unique partial constraint หรือ serialization เทียบเท่า), suggestion unique `(group_id, normalized_text)`, admin email unique, alias unique `(option_id, normalized_alias)`; compare-and-swap/row lock บังคับใน flow ที่มี single-active invariant; FO account deletion intake เป็น atomic batch (deactivate + revoke + hide + close reports + create request); การปิด report เมื่อลบบัญชีต้องให้ module ต้นทางบันทึกผลและ audit event เอง — ห้ามปิด dispute โดยไม่มี audit
- **ความทนทานต่อเหตุขัดข้อง (Fault Tolerance & SLA):**
  - Provider (email/push, The Watch API): provider failure ไม่ rollback account/invitation ที่ commit แล้ว — แสดง safe Failed/Retry state และให้ Resend ผ่าน governed flow; outbox/provider retry ต้อง idempotent + immutable attempt/result trace + ห้ามสร้าง account/invitation/notification ซ้ำ; ไม่มี retry เมื่อ destination invalid หรือ notification type ถูก disable; lifecycle email "ลบตัวตนแล้ว" ต้องส่งก่อน anonymize — ส่งไม่สำเร็จต้อง retry ก่อน anonymize personal fields ตาม product policy; market data provider unavailable/rate-limit/usage-limit = FO ใช้ cached data ล่าสุด (catalog ล่าสุดยังใช้งานได้) และแสดง error summary ใน Sync History โดยไม่ replace cache เดิม
  - Stale-state handling: ข้อมูลเปลี่ยนก่อนยืนยัน action ต้องแสดง stale state ให้ refresh/retry ไม่ใช่ commit ทับ; action error ใน confirmation modal ต้องคง modal เปิดและไม่แสดง success ปลอม
  - Availability/continuity contract: audit write fail = block high-risk action (low-risk เข้าคิว retry); ไม่มี hard delete สำหรับ invitation/audit/report record (terminal state คงไว้ตาม retention); retention cleanup เป็น system job ที่ audit ตัวเอง
  - **Open Decisions (ยังไม่ได้ตัดสินในสเปก — ห้าม assume):** ตัวเลข concurrency target (จำนวน admin พร้อมกัน, peak volume); uptime/availability SLA; RTO/RPO ของ backup/disaster recovery; rate limit ของ BO API ฝั่ง client; retry policy เชิงตัวเลขของ provider outbox (จำนวนครั้ง, backoff, dead-letter); notification broadcast throughput (Phase 2 scope — broadcast approval workflow, FCM/APNs payload contract ถูก defer พร้อม Phase 2 scoping)
